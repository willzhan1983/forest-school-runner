## 0. TL;DR（先读这 5 条）

1. **四档数值已定表**，「普通」严格等于现有数值（代数恒等，非近似）。
2. **难度选择器必须放在标题下方、角色卡片上方**——这是 960×540 里唯一能在「角色卡片（214px）+ 开始按钮（64px）不动」的前提下塞下 4 个 ≥44px 按钮的位置。角色卡片、开始按钮、底部提示坐标**零改动**。
3. **推荐默认选中「简单」**，之后记住上次选择（localStorage key：`fsr_diff`）。
4. ⚠️ **重大发现：本作存在主导策略——连续跳跃近乎无敌。** 所有障碍都贴地生成、跳跃峰值比最高障碍高 60px、无跳跃冷却/落地硬直。这直接导致**「速度」与「障碍间距」两个旋钮在超过某个阈值后完全失效**（详见 §3.4）。因此 困难/噩梦 档必须主要靠**生命数与无敌帧**拉开差距，我把生命阶梯定为 **5 / 3 / 2 / 1**。
5. ⚠️ **移动端 ≥44px 在竖屏手机上物理上不可能达成**（画布整体缩放到 0.38×）。已按横屏手机可达 44px 设计（按钮高 64），竖屏短板作为已知限制列出，需用户拍板是否追加竖屏重排。

**关键取舍说明（相对用户拍板值的补全部分）：**

- **「简单」`rampDiv=1500`（非 900）**：用户只定了起始 4.4 / 封顶 8.0，未定爬升速率。若沿用 900，则缓坡段只有 **9.0 s / 324 m** 就吃满封顶——**比普通档的 11.4 s / 576 m 还短**，等于「简单档反而更快结束新手期」，逻辑倒置。取 1500 使缓坡段延长到 **14.9 s / 540 m**，与普通档基本等长，让 10 岁玩家有一段完整的「我跑得挺好」的正反馈跑道（自我决定论的胜任感）。
- **「简单」`gapJitter` 从 170 降到 120**：降低间距方差 = 更少「突然很挤」的意外。对儿童玩家，可预测性比平均难度更重要（避免认知过载）。
- **「简单」`gapDiv=24`**：使间距触底距离 = 24×240 = 5760，与其余三档（5670~5760）**对齐在同一里程碑**。四档的「满难度阶段」都从 ~570 m 开始，方便 QA 定点复现。
- **道具是否分档调整**：**是**。护盾 = 事实上的额外一条命，是四档里最强的生存杠杆之一，必须分档。三档道具（护盾/磁铁/双倍分）**共用一个间隔参数**，`spawnPowerup()` 内部已随机三选一，**不拆分**——拆分会新增 3 组参数却几乎不增加设计价值，属于过度设计。
- **`themeAt` 四档统一 1800**：场景切换是视觉奖励不是难度旋钮；且高速下单位时间内换得更频繁，本身就是「跑得远」的正反馈。
- **`hurtTimer = 40` 四档不变**：纯视觉受击动画 + 二级保护。注意 `takeHit()` 的守卫是 `if(p.invuln > 0 || p.hurtTimer > 0) return;`，因此**任何 `invulnHit` 若低于 40 都会被 hurtTimer 掩盖**。最低档 `invulnHit = 65 > 40` ✅ 安全，但这是硬约束，未来不得把无敌帧调到 40 以下。

### 2.4 推荐默认选中项

## 🟢 推荐：首次进入默认选中「简单」，之后记住上次选择

**理由：**

1. **直接回应用户反馈**。用户明确说「难度太高」——默认落在最低档是唯一能 100% 消除该抱怨的选项。若默认「普通」，用户第二次打开仍会遇到同一个问题。
2. **10 岁是目标玩家，首因效应决定留存**。第一次就能跑起来 → 建立胜任感（自我决定论）→ 才会去尝试其他档。「先劝退再给选项」是本末倒置。
3. **不剥夺选择权**。四档全部可见并列展示，切换成本 ≈ 一次点击；最高分统一，试错无惩罚。
4. **「普通」作为基准线不会消失**，玩家熟练后自然上移——这是难度曲线的正常流动方向。

**代价（如实告知）：** 41 岁的父亲若自己打开，可能觉得简单档（封顶 8.0 vs 12.0）偏慢、不够刺激。
**缓解：** 每档按钮上直接印着体感描述与心数，差异一眼可见，换档成本极低。

**备选方案（请用户拍板）：**

| 方案 | 首次默认 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）** | 🟢 简单 | 彻底解决「太难」抱怨；儿童体验最优 | 成人首次体验偏慢 |
| B | 🔵 普通 | 保留作者原创手感作为第一印象 | **不解决用户抱怨**，用户可能再次反馈太难 |
| C | 🟢 简单 + 首启引导 | 兼顾：默认简单，并在首启时用一行高亮文字提示「觉得太 easy？试试普通 ／ 困难」 | 需额外做一次性引导逻辑（`fsr_seen_intro`） |

> **请用户在 A / B / C 中拍板。未拍板前 engineering 按 A 实现（改动最小，且直接对应用户已表达的诉求）。**

### 3.2 五处代码改造（**普通档代数恒等，非近似**）

**① 速度（原 1585 行）**

```js
// 原：Game.speed = 5.6 + Math.min(Game.distance / 900, 6.4);
var C = diffCfg();
Game.speed = Math.min(C.speedBase + Game.distance / C.rampDiv, C.speedCap);
```
等价性证明：`min(a + b, a + c) ≡ a + min(b, c)`，其中 `a = 5.6`、`c = 6.4`、`a + c = 12.0`。

**已实测验证（Node，d 从 0 扫到 20000，步长 0.37，共 54055 个采样点）：**

```
speed 最大偏差 = 0        gap 最大偏差 = 0
5.6 + 6.4 = 12  === 12.0 ? true
边界帧：d=5759 → 11.998888888888889 (两者相同)
        d=5760 → 12                  (两者相同)
        d=5721 → 11.956666666666667  (两者相同)
```

**结论：逐帧位级一致（bit-exact），不是近似，不是"肉眼无差"。** A1 验收项可直接据此判定。

### 3.4 ⚠️ 设计理论红线：主导策略「连续跳跃近乎无敌」

这是我在核对物理参数时发现的**既有设计问题**，它直接决定了我为什么把生命阶梯定成 5/3/2/1。

**事实链：**

1. `spawnObstacle()` 中**所有障碍都贴地生成**：`y: GROUND_Y - h`，最高为 `branch`（h = 60~80）。
2. 起跳 `vy = -13.2`，跳跃峰值高度 = `13.2² / (2 × 0.62)` = **140 px**。玩家碰撞盒底部在峰值时位于 `GROUND_Y - 142`，比最高障碍顶部（`GROUND_Y - 80`）**还高 62 px**。
3. **无跳跃冷却、无落地硬直**：落地即 `p.grounded = true; p.jumps = 0`，可立刻再跳。
4. **无「必须从下方滑铲通过」的悬空障碍**，滑铲在生存层面是纯可选动作。

**结论：玩家只要「落地即再跳」，即可 100% 滞空，免疫全部障碍。**

**由此推出的两个关键判断：**

**(a) 「速度」与「障碍间距」两个旋钮存在硬失效阈值。**

当障碍间隔 `T` 小于起跳滞空 `T_air = 0.710 s` 时，玩家**不可能**逐个障碍做反应，一次跳跃必然覆盖多个障碍；此时玩家的真实决策频率被钳制在 `T_eff = max(T, T_air) = 0.710 s`，**再缩短 T 也不会增加操作难度**。

| 档 | T·满速 | 是否越过阈值（T < 0.710 s） | 实际决策间隔 `T_eff` |
|---|---|---|---|
| 🟢 简单 | 0.917 s | ❌ 未越过 | **0.917 s**（可逐个反应） |
| 🔵 普通 | 0.410 s | ✅ 已越过 | 0.710 s |
| 🟠 困难 | 0.340 s | ✅ 已越过 | 0.710 s |
| 🟣 噩梦 | 0.287 s | ✅ 已越过 | 0.710 s |

> **这正是「普通档感觉太难」的机制性根因**：满速后 `T` 从 0.92 s 掉到 0.41 s，玩法从「看到障碍再跳」（儿童的自然打法）**强制切换**为「踩节奏连跳」。这是一道陡峭的**技巧悬崖**，而 10 岁玩家默认停留在悬崖下方。
> **「简单」档封顶 8.0 的真正价值就在这里**：它让 `T = 0.917 s > T_air`，**反应式打法全程成立**，悬崖被整段移除。这比单纯"慢一点"重要得多。

**(b) 困难 / 噩梦 档不能靠速度和间距拉开差距。**

上表显示三档的 `T_eff` 完全相同（0.710 s）——`speedCap` 从 12.0 提到 14.5、间距从 295 压到 250，**对熟练玩家的实际操作难度几乎零影响**。同理，**双连障碍在满速后也基本失效**（双连间距 74~114 px，而满速跳跃水平覆盖 511~618 px，一跳全清）；它只在低速开局阶段有效，因此我把 `dblFrom` 提前（普通 2200 → 困难 1400 → 噩梦 1200）来打开局压力，这是它唯一还起作用的区间。

**因此困难/噩梦的可行杠杆只剩三个**，我全部用上：

| 杠杆 | 简单 | 普通 | 困难 | 噩梦 | 说明 |
|---|---|---|---|---|---|
| 生命数 | 5 | 3 | **2** | **1** | 最强、最直观、也最"可读"的杠杆 |
| 无敌帧 | 130 | 95 | **75** | **65** | 直接提高掉血速率上限（每秒上限 = 60/帧数） |
| 护盾等道具密度 | 2× | 1× | **0.78×** | **0.72×** | 护盾 = 事实上的额外一条命 |

**掉血速率上限（每秒）= 60 / invulnHit 帧**：普通 0.63 /s → 困难 0.80 /s → 噩梦 0.92 /s。

> 📌 **给主理人的后续建议（P1，不在 DIFF-001 范围，请勿本轮实现）**：若希望让「困难/噩梦」真正靠技巧而非靠命少，需要引入**悬空障碍（需滑铲通过）**或**跳跃落地硬直**，打破「一直跳」的主导策略。这是新内容 + 新美术，属独立需求，需用户立项。
> 可选方向：① 悬空横木/吊灯（必须滑铲或走地面）② 落地 8 帧硬直 ③ 空中障碍与地面障碍交替。三选一即可，不要全加。

### 4.3 交互定义

#### A. 鼠标 / 触屏（Pointer Events）

现有架构：`pointerdown` 记录 `tapX/tapY` → `pointerup` 调 `handleMenuTap()`。难度按钮接入该流程即可，**无需新增事件监听**。

```js
function handleMenuTap(x, y){
  if(x < 0) return;
  Audio2.init();
  if(Game.state === 'menu'){
    /* ★ 难度判定必须排在最前，并 return —— 防止未来布局调整后穿透到角色卡片 */
    for(var i = 0; i < DIFF_ORDER.length; i++){
      if(hitRect(x, y, diffHitRect(i))){
        var id = DIFF_ORDER[i];
        if(Game.difficulty !== id){
          Game.difficulty = id;
          applyDifficulty();
          Audio2.diffStep ? Audio2.diffStep(i) : Audio2.click();
        }
        return;                       // ★ 命中即返回
      }
    }
    if(hitRect(x, y, picBtnRect(0))){ pickPic('cat'); return; }
    if(hitRect(x, y, picBtnRect(1))){ pickPic('owl'); return; }
    if(hitRect(x, y, cardRect(0))){ Game.charId = 'cat'; Audio2.click(); return; }
    if(hitRect(x, y, cardRect(1))){ Game.charId = 'owl'; Audio2.click(); return; }
    if(hitRect(x, y, startBtnRect())){ Audio2.click(); startGame(); return; }
  }else if(Game.state === 'gameover'){ /* 不变 */ }
}
```

**悬停态实现**：现有代码无 `mousemove` 监听。需要新增一个**轻量**的：

```js
var hoverDiff = -1;
canvas.addEventListener('pointermove', function(e){
  var p = toLogic(e.clientX, e.clientY);
  var h = -1;
  if(Game.state === 'menu'){
    for(var i = 0; i < DIFF_ORDER.length; i++){
      if(hitRect(p.x, p.y, diffBtnRect(i))){ h = i; break; }
    }
  }
  hoverDiff = h;
  canvas.style.cursor = (h >= 0) ? 'pointer' : 'default';
});
```
> ⚠️ 现有 `pointermove` 监听（403 行）开头是 `if(!Input.pointerDown) return;`。**不要改它**，另起一个监听，避免影响滑铲手势。触屏设备上 `pointermove` 只在按住时触发，因此悬停态天然只出现在有鼠标的设备 —— 这正是我们要的。

**按下态实现**：`pointerdown` 时记录 `pressedDiff = i`（同样独立监听，不改现有逻辑），`pointerup` / `pointercancel` 时清空。

#### B. 键盘

**现有 menu 态按键占用（不可破坏）：**

- `a` / `arrowleft` / `d` / `arrowright` → 切换角色
- `enter` / `空格` → `primaryAction()`（开始游戏）

**⚠️ 冲突点：`←→` 已被角色切换占用**（`a`/`d` 是它的等价键）。如果把 `←→` 改给难度，角色切换就只剩 `a`/`d`，是对现有习惯的回归破坏。

**因此采用：**

| 按键 | 行为 | 冲突检查 |
|---|---|---|
| **`1` `2` `3` `4`** | **直选** 简单/普通/困难/噩梦 | ✅ 无冲突（menu 态未占用） |
| **`↑` / `↓`** | 循环切换难度（`↓` 下一档 / `↑` 上一档，**不循环回绕**） | ✅ 无冲突（menu 态未占用；`preventDefault` 列表已含 arrowup/arrowdown） |
| `←` `→` / `a` `d` | **保持现状**：切换角色 | 不动 |
| `enter` / `空格` | **保持现状**：开始游戏 | 不动 |

> 说明：难度行在角色卡片**上方**、标题下方，`↑/↓` 是纵向语义而按钮是横向排列，映射略反直觉。但横向键已被占用，且 `1-4` 直选是主力路径（按钮上有数字角标提示）。`↑/↓` 仅作无数字键盘设备（部分平板）的兜底。**这是取舍，不是疏漏。**

```js
/* 在 keydown 的 else（非 playing）分支内追加 */
if(k >= '1' && k <= '4'){
  var id = DIFF_ORDER[parseInt(k, 10) - 1];
  if(id && Game.difficulty !== id){ Game.difficulty = id; applyDifficulty(); Audio2.diffStep ? Audio2.diffStep(parseInt(k,10)-1) : Audio2.click(); }
}
if(k === 'arrowdown' || k === 's'){
  var idx = DIFF_ORDER.indexOf(Game.difficulty);
  if(idx < DIFF_ORDER.length - 1){ Game.difficulty = DIFF_ORDER[idx+1]; applyDifficulty(); Audio2.diffStep ? Audio2.diffStep(idx+1) : Audio2.click(); }
}
if(k === 'arrowup' || k === 'w'){
  var idx2 = DIFF_ORDER.indexOf(Game.difficulty);
  if(idx2 > 0){ Game.difficulty = DIFF_ORDER[idx2-1]; applyDifficulty(); Audio2.diffStep ? Audio2.diffStep(idx2-1) : Audio2.click(); }
}
```

**键盘切换的视觉反馈**：键盘无悬停概念。切换后给目标按钮一个 **200 ms 的悬停态脉冲**（用 `Game.time` 或 `performance.now()` 计时），再落到选中态。实现成本低，避免"按了没反应"的错觉。

### 4.4 音效反馈

现有 `Audio2.click()`：`tone(760, 0.06, 'square', 0.09, 980)` —— 短促方波上滑，**可直接复用，零风险**。

**推荐（低成本高回报）：新增一个按档位变调的音效**，让"难度变高"可以被听出来，强化选择的心理权重：

```js
/* 加到 Audio2 对象内 */
diffStep:function(i){
  var f = [523.25, 622.25, 739.99, 880.00][i] || 622.25;   // C5 / D#5 / F#5 / A5
  this.tone(f, 0.07, 'square', 0.10, f * 1.35);
  this.tone(f * 2, 0.05, 'triangle', 0.05, f * 2.6, 0.05);
}
```
音高沿 C → D♯ → F♯ → A 递增（增三和弦上行），档位越高听感越"紧"，与配色（绿→蓝→橙→紫红）的紧张度递进一致。

> **两种方案请 engineering 二选一：复用 `Audio2.click()`（零改动）或新增 `diffStep()`（+3 行）。** 我推荐新增。

| **② 暂停面板** | 档位名 + 完整描述 | 暂停遮罩中央偏下，`bold 24px` 档位名（`base` 色）+ `15px` 完整描述（`rgba(255,255,255,.8)`） | **P0** |
| **③ 结算页**（最关键的公平性补偿） | `难度 · 普通` | 数据面板（`px=250, py=140, pw=460, ph=250`）**正下方、最高分文字上方**，`W/2`, baseline `py + ph + 10`（= 400），`bold 16px`，`base` 色 | **P0** |

> **③ 是统一最高分方案的必要补偿。** 四档共用一个 `fsr_best`，若结算页不显示难度，玩家无法判断"这个纪录是在哪一档拿的"，纪录的意义会被稀释，长期会削弱成就感。详见 §5.1 风险 R3。
> 若 `py+ph+10 = 400` 与最高分文字（baseline `py+ph+34 = 424`）过近，可将面板 `ph` 从 250 增至 268（面板底 408），两行间距 16px。**这是唯一需要微调的既有坐标。**

### 4.7 移动端适配

#### ⚠️ 先说结论：竖屏手机上 ≥44 CSS px 物理上不可达

`resize()` 采用等比缩放：`s = min((innerW−24)/960, (innerH−24)/540)`。实测换算：

| 设备 / 姿态 | 缩放 s | 难度按钮 64 逻辑px → 实际 CSS px | 达标？ |
|---|---|---|---|
| 桌面 1920×1080 | 1.11 | 71 px | ✅ |
| iPad 820×1180 | 0.829 | 53 px | ✅ |
| iPhone 竖屏 390×844 | **0.381** | **24 px** | ❌ |
| iPhone 横屏 844×390 | 0.678 | **43 px** | ⚠️ 临界（≈44） |

**这是本作既有问题，不是难度选择器引入的**：现有开始按钮（64px）在竖屏手机上同样只有 24 CSS px，暂停/音乐按钮（56px）只有 21 CSS px。

**已采取的措施：**

1. **按钮高从 58 提到 64** —— 使横屏手机达到 43 CSS px（≈44），且不破坏 `y=208` 的卡片定位（见 §4.1 校验）。
2. **命中区外扩** `diffHitRect()`：向上 +10px、左右各 +2px（见 §4.1）。在任意缩放下都提升容错。
3. **判定顺序优先**：难度按钮在 `handleMenuTap` 中最先判定并 `return`，即使小屏误触偏移也不会触发下方的角色卡片。

**仍需用户拍板的两个选项（二选一）：**

| 选项 | 做法 | 成本 | 效果 |
|---|---|---|---|
| **M1（推荐，先不做）** | 接受现状，依赖已有的竖屏提示条（`showTipTemporarily()`，4 秒自动收起）引导横屏 | 0 | 竖屏仍偏小，但横屏达标，且这是全作统一问题而非难度模块特例 |
| **M2** | 竖屏检测（`innerH > innerW*1.05`）时难度行切换为 **2×2 网格**：按钮 `w=300, h=72`，`x = 100 / 480`，`y = 120 / 202` | 中（需重排卡片/开始按钮，或改为竖屏专用菜单页） | 竖屏按钮达 27 CSS px，仍不达标，**性价比低** |

> **建议选 M1。** 理由：M2 投入产出比差（做了也到不了 44px），且竖屏下整个画布只有 366×206 CSS px，**所有元素都小**，单独放大难度按钮会造成视觉失衡。真正的解法是「竖屏专用布局」这一独立改造项，应单独立项，不应塞进 DIFF-001。

### 4.8 持久化

| 项 | 值 |
|---|---|
| **Key** | **`fsr_diff`** |
| Value | `'easy'` / `'normal'` / `'hard'` / `'nightmare'`（字符串，非索引——可读、抗重排） |
| 写入时机 | `applyDifficulty()` 内，即每次切换时立即写入 |
| 读取时机 | 与现有 `fsr_best` / `fsr_music` 同处（438-440 行区域） |
| 缺省值 | `'easy'`（默认方案 A；若用户选 B 则改 `'normal'`） |
| 异常处理 | 值不在 `DIFF_ORDER` 中时静默回退 `'normal'`，**不抛错、不清理 localStorage** |

```js
/* 放置在 440 行 fsr_music 读取之后 */
Game.difficulty = 'easy';                                   // 默认（方案 A）
try{
  var _d = localStorage.getItem('fsr_diff');
  if(_d && DIFF_ORDER.indexOf(_d) >= 0) Game.difficulty = _d;
}catch(e){}
applyDifficulty();                                          // 同步 maxLives / lives
```
> 现有 localStorage key 家族：`fsr_best` / `fsr_music` / `fsr_pic_cat` / `fsr_pic_owl`。`fsr_diff` 命名一致 ✅。

## 5. 边界与风险

### 5.1 实现时容易踩的坑（8 条）

#### R1 【高危】游玩中切换难度会静默扣血
`applyDifficulty()` 若直接写 `Game.lives = C.maxLives`，在**已开局**状态下按数字键会立刻把血量改成新档上限（例如普通 3 → 噩梦 1，玩家瞬间只剩 1 血）。
**规避**：`applyDifficulty()` 内加守卫 `if(Game.state !== 'playing') Game.lives = C.maxLives;`（已写入 §3.3）。更彻底的做法是 **在游玩状态（`playing` / `paused`）下完全屏蔽难度切换键**。
**建议**：两者都做——守卫 + 屏蔽，双保险。

#### R2 【高危】暂停时能否切难度
暂停界面若显示当前难度（§4.6 ②），玩家很可能尝试在暂停时改难度。**必须禁止**：`maxLives` 变化会导致 HUD 心形数量中途改变（现有 `drawHeart` 循环 `Game.maxLives`），若 `Game.lives > maxLives` 会出现"空心比满格多"的错乱，且速度/间距突变会让当前这一局的性质说不清。
**规格**：暂停界面**只显示、不可改**；暂停态下屏蔽 `1-4` / `↑↓` 难度键。想换难度必须回主菜单（结算页 → 「换个小伙伴」回 `menu`）。

#### R3 【高危】统一最高分下的跨难度刷分
用户已拍板统一记录，故不改。但必须认知后果：**「简单」档（5 命 + 慢速 + 双倍道具）在单位时间得分效率上可能高于「普通」档**，理性玩家会被激励在简单档刷分，最高分的意义被稀释。
**缓解（已纳入规格）**：结算页强制显示难度（§4.6 ③），让玩家自己知道纪录归属。
**未来可逆**：若日后要分档记录，改动面极小——`localStorage.setItem('fsr_best', ...)` 改为 `'fsr_best_' + Game.difficulty`，读取处同步即可。**现在统一不影响将来拆分**，不必现在纠结。

#### R4 【高危】`gameOver` 后重开是否正确保持难度
`startGame()` 会重置 `lives / distance / speed` 等，但**不会重置 `Game.difficulty`**（它不在此函数内）——这是正确的，难度应保持。但有两个具体陷阱：
1. `Game.speed = 5.6` 是**硬编码**（1557 行），必须改为 `diffCfg().speedBase`，否则**任何档位开局第一帧都会按 5.6 起步**，在简单档表现为"开局突然偏快，一帧后才降回 4.4"。一帧影响极小但会造成 0.016 s 的位移误差，且是明显的坏味道。
2. 结算页的「再跑一次」→ `startGame()` 直接重开，**不经过菜单**。需确认此时 `Game.maxLives` 仍是上一局的值（未走 `applyDifficulty`）。因 `Game.difficulty` 未被改动，`maxLives` 保持正确 ✅，但**必须在 QA 中实测一次**。

#### R5 【中】生命数变化破坏既有 HUD 假设
现有 `drawHeart(W - 40 - i*42, 44, 32, ...)` 隐含假设最多 3 颗心。简单档 5 颗心时最左侧心位于 `x = 920 − 4×42 = 752`，与居中距离文字（`"576 m"` 22px，约 70px 宽，占据 `445..515`）**无重叠** ✅，与音乐按钮（`x=80..136`）也安全 ✅。
但需实测：距离文字在长局会变成 `"1234 m"`（约 85px 宽，`437..522`），仍安全。**噩梦档 1 颗心**时 HUD 右侧会显得空——可接受，这本身就是"你很脆弱"的视觉信号。

#### R6 【中】`resetWorld()` 的初值必须随档位
`resetWorld()` 中 `nextPlatformAt / nextPickupAt / nextPowerupAt` 是硬编码初值（1393-1400 行），若只改生成处（1752/1756/1760 行）而漏改初值，则**每局开局前几个 spawn 会用错档位的节奏**，且只在 `resetWorld` 后第一次生成时暴露——是典型的"偶发难复现"bug。
**规避**：§3.2 ⑤ 已明确两处都要改。**QA 请重点验这一条。**

#### R7 【中】数字键 `1-4` 与浏览器/输入法
`e.key.toLowerCase()` 在部分输入法激活状态下可能返回非 ASCII 数字（如全角 `１`）。建议判定用 `e.code`（`Digit1`~`Digit4`）更稳，或同时接受 `e.key` 与 `e.code`。**低成本，建议直接用 `e.code`。**

#### R8 【低】`Infinity` 参与比较
`easy` 档 `dblFrom = Infinity`，`Game.distance > Infinity` 恒为 `false`，配合 `dblProb > 0` 短路是安全的。但**若将来有人把代码改成 `Math.random() < C.dblProb && Game.distance > C.dblFrom` 之外的形式，或把 `dblFrom` 序列化进 JSON，`Infinity` 会变成 `null` 并导致 `distance > null` 恒真**。
**规避**：`easy` 档改用 `dblFrom: 1e9`（大数）替代 `Infinity`，或保留 `dblProb > 0` 短路并加注释。**建议用 `1e9`**，零风险。

## 6. 预期存活时长与 QA 验收

### 6.1 粗估（**模型已披露，仅供排序参考，不作为验收标准**）

> ⚠️ 以下为解析模型估算，**误差可能达 ±50%**。真正的验收标准见 §6.2 的客观指标与 §6.3 的主观测试。请勿把倍数当承诺。

**模型假设：**
1. 玩家的真实决策间隔 `T_eff = max(T, T_air)`（跳跃必然覆盖多个障碍时，一次跳跃 = 一次决策）。
2. 单次决策失误率 `p(T) = clamp(0.03 + 0.30 × max(0, (1.25 − T) / 0.95), 0.03, 0.40)`。
3. 死亡周期 = `invulnHit/60 + T_eff / p`（无敌帧 + 平均存活到下次失误的时间）。
4. 预期存活 = `maxLives × 死亡周期`；总时长 ≈ 缓坡耗时 + 满速段存活。

| 档 | 满速 `T_eff` | `p` | 死亡周期 | × 命数 | 满速段存活 | + 缓坡 | **总时长（粗估）** | **相对普通** |
|---|---|---|---|---|---|---|---|---|
| 🟢 简单 | 0.917 s | 0.135 | 8.96 s | ×5 | 44.8 s | +14.9 s | **≈ 60 s** | **≈ 2.2×** |
| 🔵 普通 | 0.710 s | 0.201 | 5.11 s | ×3 | 15.3 s | +11.4 s | **≈ 27 s** | **1.0×（基准）** |
| 🟠 困难 | 0.710 s | 0.201 | 4.78 s | ×2 | 9.6 s | +10.1 s | **≈ 20 s** | **≈ 0.74×** |
| 🟣 噩梦 | 0.710 s | 0.201 | 4.62 s | ×1 | 4.6 s | +8.5 s | **≈ 13 s** | **≈ 0.48×** |

**给 QA 的口径：预期倍数区间 —— 简单 2.0~3.5× ｜ 普通 1.0× ｜ 困难 0.6~0.85× ｜ 噩梦 0.3~0.6×。**
超出区间即说明有实现错误（尤其注意 R4、R6）。
